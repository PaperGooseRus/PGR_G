# Оптимизация по памяти и типовым операциям

## Конкретные изменения относительно v0.1

| Участок | Было | Стало | Эффект |
|---|---|---|---|
| Статическая карта | `std::vector<Obstacle>` + `std::vector<Npc>` с выделениями в куче | `inline static constexpr std::array` | Нет выделений на создание мира, данные живут статически |
| Объект `World` на x86_64 | `sizeof(World) == 48` байт плюс динамическая память | `sizeof(World) == 1` байт, данные отдельно статические | Меньше состояние экземпляра; **не значит**, что все данные карты занимают 1 байт |
| Поиск интерактивного объекта | `sqrt` для каждого сравниваемого объекта | Квадрат расстояния без `sqrt` | Меньше математических операций на частом пути |
| Дорожки | 46 вызовов `DrawCube` на кадр | 2 вызова `DrawCube` | Минус 44 вызова прорисовки на кадр |
| HUD с открытым диалогом | `std::string` из `const char*` каждый кадр | Готовые `const char*` без сборки строк | Нет временных строк и потенциальных аллокаций |
| Связь модулей | `render.hpp -> player.hpp -> world.hpp` | Общий `api/contracts.hpp`; связывание только в `Application` | Отдельное компилирование и тестирование логики |

Числа `sizeof` получены `g++` в 64-битной Linux-среде. Общий объём RAM зависит от компоновки, выравнивания, реализации raylib и среды исполнения. Отдельный microbenchmark здесь не заявлен как доказательство FPS: без реальной видеокарты такое сравнение некорректно.

## Почему не использованы другие оптимизации

* **Octree, quad-tree и ECS** не нужны для 19 препятствий и четырёх NPC; они усложняют структуру и добавляют память.
* **Ручной пул аллокаций** не нужен: в клиентском игровом цикле наши контейнеры вообще ничего не выделяют.
* **Многопоточность** повредит простоте и усложнит контракт владения при такой сцене.
* **`-Ofast`** не используем, чтобы не жертвовать предсказуемостью арифметики; `-O2` достаточно.
* **Кэширование камеры** не делаем: её положение зависит от движения и поворота каждый кадр.

## Тестируемые характеристики

1. `test_modules`: число объектов, допустимость перемещения, скольжение по стене, прыжок, целевая дистанция, работа с произвольным `SceneView`.
2. `check_dependencies.py`: запрещает `#include` другого модуля и старого ядра внутри `src/modules`.
3. `test_client_stub`: компилирует полный `src/main.cpp` с упрощёнными функциями raylib и делает один безоконный кадр. **Не тестирует графику на настоящей GPU.**
4. Сохранённые прежние тесты `core_v3` подтверждают, что отделённый CLI не повреждён.

## Следующие измерения после установки raylib

Проверить фактическую работу на целевой Windows: число FPS, время кадра, общее потребление RAM и время движения рядом с несколькими препятствиями. Для этих тестов нужно запускать настоящую программу, а не заглушку raylib.
