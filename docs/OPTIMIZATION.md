# Экономия памяти и быстрые типовые операции

## Архитектурные решения

- Статический массив препятствий/NPC по-прежнему не выделяется в куче на каждом кадре.
- Новая экономика не связана с рендерером: нет SQL-запросов внутри `Renderer::scene()` и `Renderer::hud()`.
- В обычном кадре производится только дешёвый поиск ближайшего объекта по квадрату расстояния и отрисовка уже подготовленных данных.
- `InventorySnapshot` и `EventRecord` обновляются по действиям (`E`, `T`, `C`, `R`, `I`, `J`), а не на каждом кадре.
- Природа обновляется по абсолютному времени с интервалом опроса ~1 секунда. Ни дерево, ни NPC не требуют отдельного потока.
- SHA-256 состояния вычисляется только при модификации экономических данных; это не «каждый кадр».
- Двухфазная логика сделки минимизирует состояния: OPEN (резерв) → DONE или CANCELLED.
- Нет рендеринга из Blender-моделей; всё нарисовано простыми примитивами.

## Компромиссы и будущие улучшения

`state_hash()` сейчас проходит по таблицам текущего мира после каждого экономического события. Для маленького прототипа это обеспечивает простую проверку целостности. В будущем с тысячами игроков и миллионами предметов потребуется использовать инкрементальный Merkle root, снапшоты и пакетное журналирование.

`LedgerStore` пока в виде одного SQL-модуля для сокращения объёма кода и числа зависимостей. Не стоит вводить десятки вспомогательных шаблонов и абстракций без профиля производительности. При появлении реальной нагрузки сначала измеряем SQLite profiler, частоту событий, время коммита и FPS, затем оптимизируем.
