# Безопасность реестра и торговых контрактов

## Модель угроз

Локальная игра доверяет своему исполняемому коду и файлу `save/game.sqlite`. Защита доступа через API рассчитана на подключение к будущему серверу. В текущем однопользовательском варианте владелец ПК имеет полный доступ к данным и может переписать цепочку полностью. Поэтому **локальные редкие предметы нельзя автоматически импортировать в будущую сетевую экономику**.

## Что защищено сейчас

1. **Атомарность:** команда меняет ресурс, инвентарь, владельца, активное предложение и журнал в одной транзакции SQLite.
2. **Escrow:** предложение временно резервирует актив. Повторное подтверждение, двойная продажа одного уникального предмета и торговля отсутствующим ресурсом отклоняются.
3. **Авторизация API:** доступ к инвентарю и частным сделкам есть только у владельца/участников, если `observer` взят из доверенной сессии. Передача произвольного ID от клиента в будущем должна быть запрещена.
4. **Контроль целостности:** SHA-256 по (предыдущий хеш, последовательный номер, timestamp, автор, второй участник, тип, полезная нагрузка, публичность, **состояние БД**). Пересчёт при каждом старте выявляет подмену события или активного баланса. Правило синтеза закреплено commitment в генезисе с 128-битной случайной солью, чтобы публичный хеш нельзя было перебрать по 64 вариантам без знания соли.
5. **Редкость:** `RAND_bytes` + rejection sampling; шанс успеха для подходящей попытки ровно 1 / 1 000 000. Уникальность гарантирует `PRIMARY KEY` открытия `element:1024`.

## Что НЕ защищено

- Настоящая неизменяемость без внешнего якоря: администратор может переписать файл БД и всю хеш-цепь с пересчётом хешей.
- Проверка справедливости броска третьей стороной: `RAND_bytes` не является VRF. Не создаём впечатление независимой криптографической лотереи.
- Игроки без сервера: `ActorId` пока не привязан к сетевой аутентификации, нет защиты от подделки клиента.
- Шифрование приватных данных на диске: другой пользователь ОС с доступом к файлу SQLite может прочитать его. На сетевой версии сервер должен выдавать только приватные DTO.
- Журнал — не полноценный механизм воспроизведения всех состояний после удаления БД. Он предназначен для аудита; необходимы резервные копии.

## Дальнейшие шаги

1. Вынести `LedgerStore` и симуляцию на авторитетный сервер.
2. Связать персонажа с проверенной сессией; не доверять идентификаторам и случайным исходам от клиента.
3. Использовать request-id/idempotency для повторных сетевых пакетов и лимиты на запросы.
4. Периодически публиковать подписанный хеш последнего события в независимом публичном источнике.
5. При существенной экономической ценности рассмотреть VRF и публичные аудиторские доказательства, а не самостоятельную криптовалютную цепочку.
