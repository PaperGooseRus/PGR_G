# Архитектура RPG 3D Client v0.1-refactor

## Контракт на зависимости

```text
                    src/main.cpp
                   class Application
        ┌────────┬────────┼────────┬──────────┬──────────┐
        │        │        │        │          │          │
       World  Movement Collision Interaction Camera   Renderer
        │        │        │        │          │          │
        └────────┴────────┴────────┴────┬─────┴──────────┘
                                       │
                            api/contracts.hpp
```

* Модули в `src/modules/` **не включают друг друга**. Каждый знает только `api/contracts.hpp` и собственные системные заголовки. `camera.hpp` и `renderer.hpp` дополнительно используют `raylib.h`.
* `Application` в **единственном** `src/main.cpp` является компоновщиком: получает данные у `World`, передаёт их в `Collision`, `Movement`, `InteractionSystem`, `CameraSystem`, `Renderer`.
* Общий контракт содержит только простые типы, невладеющие `View`, ссылки на NPC и значения. У него **нет** логики игровой сцены, рендеринга, аллокаций и зависимости от raylib.
* Нет интерфейсного зоопарка, фабрик, DI-контейнеров, виртуальных базовых классов или серверного кода. Отдельные статические алгоритмы проще проверить и переиспользовать.

### Границы модулей

| Модуль | Читает | Изменяет | Не делает |
|---|---|---|---|
| `World` | Собственные константные массивы | Ничего | Не считает коллизии, не вызывает raylib |
| `Movement` | `Player`, `MovementInput`, `dt` | Высоту/скорость прыжка | Не знает карту, не перемещает игрока сквозь стены |
| `Collision` | `SceneView`, координаты | Ничего | Не принимает ввод, не занимается анимацией |
| `InteractionSystem` | `SceneView`, координаты | Ничего | Не выдаёт ресурсы, не вызывает NPC |
| `CameraSystem` | `SceneView`, `Player`, углы | Ничего | Не читает кнопки, не рисует |
| `Renderer` | `SceneView`, `Player`, `HudState` | Только текущий кадр raylib | Не меняет игровую логику |
| `Application` | Ввод и состояния из модулей | `Player`, UI-состояние | Не содержит алгоритмов симуляции |

### Последовательность кадра

1. `Application::update` читает клавиши и мышь.
2. `Movement::step(player, input, dt)` возвращает **запрошенный** `Vec2`, отдельно обновляет высоту прыжка.
3. `Collision::slide(scene, position, delta)` возвращает допустимую позицию. Только `Application` присваивает её игроку.
4. `InteractionSystem::closest(scene, position)` выбирает объект. `Application` изменяет состояние диалога.
5. `CameraSystem::make(scene, player, ...)` строит `Camera3D`.
6. `Application::draw` управляет `BeginDrawing`/`BeginMode3D`; `Renderer` рисует только данные.

Это также означает, что чистая игровая логика собирается **без raylib и без окна**.

## Владение памятью

* `World` не владеет динамической памятью: массивы `inline static constexpr std::array` находятся в статическом хранилище. `sizeof(World)` в нашей 64-битной сборке — 1 байт; размер самого статического массива объектов этим измерением не учитывается.
* `SceneView` содержит пару `View<T>` и размер карты; каждый `View` — указатель и количество. Он **не владеет** памятью, не возвращается из временного динамического контейнера и годится только пока жив источник. В данной версии данные `World` статические.
* В `Application` лежат `Player` и несколько скаляров. Нет менеджеров сцен, событийных очередей и других выделяющих память контейнеров.
* `Renderer` не использует `std::string`, `std::vector` или `new`; строки NPC разделены заранее.
* Вызовы raylib имеют свои внутренние затраты, которые не контролируются этими правилами. Здесь утверждается только отсутствие **наших** аллокаций в цикле.

## Существующее RPG Core v3

Папка `core_v3/` сохранена **без изменений**. Её CLI и прежние тесты продолжают собираться отдельно. Внутренние заголовки legacy-ядра всё ещё зависят друг от друга (`crafting.hpp -> game_state.hpp -> elements.hpp`): это **не часть завершённого рефакторинга**. Новые правила независимости относятся к `src/modules/`. Мы специально не переписывали сохранения и алхимию при изменении графического клиента.

Для следующего этапа введём адаптер RPG Core → структуры клиента. Сначала определим стабильный контракт команд (`GatherRequest`, `CraftRequest`) и результатов; только `Application` будет вызывать его. Никаких включений `crafting.hpp` в `Renderer`.

## Ограничения

* Карта неизменяема и мала; сложный spatial index пока только увеличит память и код.
* Камера проверяет 19 AABB за кадр; для многотысячных карт понадобится пространственное разбиение.
* Столкновение дискретное; физика прыжка пока только визуальная.
* Индексы `Interaction` привязаны к текущему `SceneView`, это не глобальные ID предметов. При подключении Core v3 понадобятся устойчивые идентификаторы.
* Клиент — локальная программа. Сетевой/публичный ABI не зафиксирован, структура `SceneView` может развиваться между версиями.
