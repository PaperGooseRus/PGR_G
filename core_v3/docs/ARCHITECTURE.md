# Архитектура RPG Crafting Core v3

## Цель

Разделить предметную модель, правила профессий и хранение данных так, чтобы будущий GUI, игровой движок или сетевой сервер могли использовать те же алгоритмы без переписывания ядра.

## Модули

```text
main.cpp (CLI)
   │
   ├── crafting.hpp    ← операции и проверки существующих ресурсов
   │       ├── game_state.hpp ← данные, загрузка/сохранение
   │       │        └── elements.hpp ← элементы и старый односвязный список
   │       └── alchemy.hpp    ← чистые правила реакции
   │                └── elements.hpp
   └── alchemy_history.hpp ← только чтение старых журналов

storage.hpp ← инфраструктура файловой записи
```

**Правила зависимостей:** `GameState` не вызывает код CLI. `Engine` управляет игровыми действиями, но не открывает файлы. За снимок отвечает консольный адаптер. Старые правила из `alchemy.hpp` переиспользуются, не дублируются в `GameState`.

## Сущности

- **Actor** — личность игрока или NPC, направление, история ритуальных действий.
- **Skill** — независимый профессиональный опыт `actor + profession → xp`; уровень вычисляется, а не хранится вторым полем.
- **ResourceNode** — конечное месторождение (`remaining`); без ресурса выдача `Lot` запрещена.
- **Lot** — уникальный экземпляр или стек материала с владельцем, количеством, номером первичного элемента, формой, качеством и ссылками `source1/source2` на исходные лоты.
- **Item** — уникальный предмет, ссылается на физические исходники. Деталь изделия может быть встроена в другой предмет (`owner=0`), но остаётся в истории.
- **WorkOrder** — заказ на конкретную операцию, два входных ID, исполнитель, заказчик, статус, результат. До исполнения входы резервируются.
- **Discovery** — редкая аномалия, впервые обнаруженная на определённом предмете.
- **Knowledge** — эффект, исследованный конкретным персонажем; можно передавать другому.
- **GameEvent** — короткая история действий для аудита и проверки.

## Алгоритм `perform`

1. Проверить персонажа, количество входов, владение ими, свободность от резервов и структурную совместимость материалов/компонентов.
2. Определить уровень профессии, вероятность успеха и случайный исход. Для алхимии используется базовая `alchemy::chances()` плюс небольшой бонус от навыка.
3. Создать новый лот/предмет либо обновить существующий (инкрустация, настройка). При сборке ребёнок ссылается на реальные детали.
4. Израсходовать реагенты; при успешной сборке пометить дочерние детали встроенными. Неудачная сборка не уничтожает сами компоненты.
5. Начислить опыт, проверить необычные условия, записать открытие и событие.
6. В адаптере CLI проверить результат `validate_state`, записать полный снимок на диск, только после успешного сохранения заменить исходный `GameState`.

Таким образом **неуспешная валидация не изменяет данные**, а отказ записи Markdown не подтверждает изменения в памяти игрового процесса.

## Границы абстракций

Крафт пока определяется **операцией и типами её физических входов**, а не конкретными ID элементов. Например, `forge` требует металл с качеством и свойствами; `decorate` требует готовый экземпляр меча и камень. Это не полноценная генерация топологий предметов: в текущем прототипе клинок и рукоять являются известными категориями. Позже их можно заменить графом деталей с интерфейсами соединения.

`std::vector` используется для коллекций экономических сущностей; отдельный односвязный список `ElementList` по-прежнему существует и сериализуется в `elements.md`, как было запрошено в v1.

## Точки расширения

- Разнести операции по профессиям через интерфейсы `IOperationRule`, не меняя `Lot` и `Item`.
- Добавить генератор физических характеристик заготовок, допуски соединений и типизированные свойства.
- Ввести серверный `IWorldRepository`, который гарантирует конкурентную транзакционность и скрывает серверные seed.
- Добавить действия NPC-планировщика, не предоставляя ему особых прав на материализацию ресурсов.
- Добавить пакетную симуляцию и профилирование без UI.
