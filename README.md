# Кубическая деревня — RPG 3D v0.2 (экономика и реестр событий)

**Одиночный 3D-прототип на русском языке.** C++17, raylib, SQLite и OpenSSL. Создан для одного разработчика на Windows / MSYS2 UCRT64. Никаких 3D-моделей, платных ассетов, Blender, серверов и криптокошельков.

В этой версии 3D-клиент связан с **новой локальной подсистемой общей добычи, приватного инвентаря, игрового золота/серебра, торговых контрактов и редких открытий**. История операций сохраняется в SQLite и связывается SHA-256. Прежнее экспериментальное `core_v3` (химические элементы, алхимия, кузнечные заказы и навыки) сохранено как самостоятельный **legacy CLI**, но ещё **не использует** новую экономическую БД. Это важное ограничение текущего прототипа.

## 1. Установка

Открой **MSYS2 UCRT64** и выполни:

```bash
pacman -Syu
pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-raylib \
          mingw-w64-ucrt-x86_64-sqlite3 mingw-w64-ucrt-x86_64-openssl
```

Нужные инструменты: VS Code, GCC/MSYS2; CMake и Python необязательны для обычной сборки. Из корня распакованного проекта:

```bash
./build.sh
./build/rpg_3d.exe
```

Или открой `build.cmd`, затем `run.cmd` в Windows. На компьютере должен иметься **системный шрифт с кириллицей** (Windows Segoe UI/Arial). Шрифты и модели не входят в архив. Интерфейс игры полностью на русском. Важно, чтобы текущим каталогом при запуске был каталог проекта: там находится `save/`.

> Внимание: **файлы `save/game.sqlite` НЕ включены в архив**. На первом запуске создаётся новая экономика. Старые `elements.md`, `alchemy.md`, `world_state.md` находятся в `core_v3/` и **не мигрируются автоматически** в новый SQLite.

## 2. Управление

| Клавиша | Действие |
|---|---|
| WASD, мышь | Перемещение и поворот камеры |
| Shift / Space | Бег / прыжок (фиксируется в истории мира) |
| E | Добыть дерево/руду/кристалл либо поговорить с NPC |
| I | Показать **только свой** инвентарь |
| J | Показать публичные и разрешённые личные события |
| T у алхимика | Создать предложение: 1 руда за 10 золота |
| C у алхимика | Обменять 5 золота на 20 серебра |
| P у алхимика | Молитва не чаще одного раза за игровой день (45 с) |
| R у алхимика | Попробовать редкий синтез №1024 после скрытых условий |
| F1 / Tab | Справка / освободить курсор |
| Escape | Выйти |

NPC проверяет фиксированные условия предложенной сделки и автоматически подтверждает её с небольшой задержкой. Незаконченный заказ восстанавливается при следующем запуске. Если NPC не может оплатить покупку, предложение отменяется с возвратом зарезервированного имущества.

## 3. Что реально работает

1. **Общий мир.** У деревьев, древесины, рудных жил и камней с кристаллами общий конечный запас. Извлечённые ресурсы поступают в личный инвентарь. Добыча и зачисление проходят в одной транзакции. Запас природных ресурсов восстанавливается по времени, включая время между запусками.
2. **Приватность по API.** `LedgerStore::inventory(observer,owner,out)` выдаёт данные только при совпадении идентификаторов. Это проверено и на двух тестовых игроках. Прямое чтение локального файла БД владельцем ПК не запрещено: это не сетевой сервер.
3. **Игровые деньги.** Раздельные целочисленные балансы золота и серебра. Их можно обменивать по договору. `float` для валют не используется.
4. **Торговые контракты.** Предложение резервирует актив продавца (escrow). Покупатель принимает только исходные условия; обмен исполняется как одна транзакция SQLite. Отмена возвращает резерв. Уникальный предмет можно зарезервировать и передать ровно один раз.
5. **Реестр событий.** У каждой операции есть номер и SHA-256. Хеш включает предыдущую запись **и контрольную сумму состояния** (инвентари, валюты, предложения, предметы, ресурсы, ритуалы, правила). Commitment на скрытые условия использует 128-битную соль. Несогласованная правка старой записи или текущего баланса обнаруживается при запуске.
6. **Открытие №1024.** У каждого мира есть случайные скрытые условия (число прыжков, число игровых дней молитв, направление взгляда). При их выполнении можно потратить 2 руды + 1 древесину + 1 кристалл и попытаться создать единственный элемент №1024. На каждую допустимую попытку шанс ровно **1 / 1 000 000**. Исход выбирается через `RAND_bytes`, без смещения по модулю. Успешный предмет получает уникальный ID, первооткрывателя и событие происхождения. Его можно продать по общей системе сделок через API (отдельный экран торговли уникальными предметами появится позже).

**Вероятность открытия не гарантирует, что один из миллиона игроков обязательно выиграет.** Нельзя считать текущий локальный файл SQLite независимым доказательством серверной честности или подтверждением VRF.

## 4. Техническая структура

```text
src/
├── main.cpp                       # class Application: единственная композиция
├── api/
│   ├── contracts.hpp              # Геометрия, HUD, невладеющие DTO
│   └── economy_contracts.hpp      # Объекты торговли, доступа и открытий
└── modules/
    ├── world.hpp                  # Статическая кубическая карта
    ├── collision.hpp              # Столкновения
    ├── movement.hpp               # Кинематика
    ├── interaction.hpp            # Поиск ближайшего NPC или ресурса
    ├── camera.hpp                 # Камера raylib
    ├── renderer.hpp               # 3D + русский HUD, системный шрифт
    ├── trade_rules.hpp            # Чистые правила сделки и политики NPC
    ├── rare_discovery.hpp         # Чистые правила аномалии, CSPRNG
    └── ledger_store.hpp           # SQLite + SHA-256, атомарные операции
core_v3/                            # Старое ядро; самостоятельно
save/game.sqlite                    # Новое локальное сохранение; генерируется
CMakeLists.txt, build.cmd, build.sh, run.cmd
Doxyfile, docs/, tests/
```

Модули не включают заголовки друг друга. Данные передаются через `src/api/*.hpp`, вызовы соединяются **только в `Application`**, а `Renderer` не изменяет игровое состояние. Горячий цикл не создаёт строки или векторы в каждом кадре; снимки и события обновляются по действиям пользователя. Каждый публичный API имеет русскоязычные Doxygen-комментарии (включая требования, предупреждения и код результата).

## 5. Сборка и тесты CMake

Без графического устройства и raylib можно проверить логику с тестовой заглушкой:

```bash
cmake -S . -B build-test -DRPG_BUILD_CLIENT=OFF -DRPG_BUILD_STUB_SMOKE=ON -DBUILD_TESTING=ON
cmake --build build-test -j 4
ctest --test-dir build-test --output-on-failure
```

С установленной raylib:

```bash
cmake -S . -B build-client -DRPG_BUILD_CLIENT=ON -DBUILD_TESTING=ON
cmake --build build-client
```

Для проверки БД без окна из каталога проекта:

```bash
./build/rpg_3d.exe --verify
./build/rpg_3d.exe --inventory
./build/rpg_3d.exe --audit
```

Автотесты включают добычу двух игроков из одного месторождения, запрет чужого инвентаря, сделки и валютные обмены, откат резервов, отсутствие двойной оплаты, единственное открытие №1024, передачу уникального предмета, перезапуск и обнаружение подмены данных. Тестовый принудительный успех синтеза **не доступен** через игровое управление.

## 7. Честные ограничения

- **Не blockchain:** журнал связан SHA-256 внутри SQLite; внешний якорь, VRF, распределённые узлы и цифровые подписи пока отсутствуют. Обладатель полного доступа к ПК способен переписать файл, пересчитать хеши и обмануть локальную систему.
- **Не настоящий мультиплеер:** два игрока моделируются тестами, но сетевого сервера/авторизации пока нет. Не принимай клиентские ActorId за доверенные личности.
- **Не многопоточный сервер:** один поток последовательно изменяет SQLite. NPC выполняет небольшой сценарий торговли с задержкой; автономные производственные цепочки из `core_v3` ещё не связаны с новым хранилищем.
- **Нет продвинутого крафта в 3D:** сохранённый `core_v3` пока работает через собственную CLI. В 3D уже есть добыча и экономические операции, не завершена интеграция классов и алхимии.
- **Визуализацию на живом окне raylib здесь не удалось проверить**, потому что в среде разработки нет raylib и графического дисплея. Тестовый графический кадр выполнен с API-заглушкой. Финальная визуальная проверка остаётся на ПК с MSYS2 UCRT64.
